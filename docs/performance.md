# Qwen3.5-2B 性能优化记录

2026-11-13,Pi 4 / Cortex-A72,同一个已校验的 Q4_0 GGUF。基线源码树为 GitHub 提交 `d93289b`（与本地原提交 `fea517a` 文件树相同）。

## 改动

1. Q6_K 每个 256 元素块的缩放整数点积,先在四个 int32 向量通道累加,块末只做一次水平归约。每块最坏整数和小于 `256 * 32 * 127 * 128 < 2^27`,不会溢出 int32,保持块级浮点累加顺序。
2. 分块矩阵的预取流每处理一个输入块前进四行的字节数。tile 的权重地址已包含 `t * block_bytes`,额外加 `3 * t * block_bytes`,让预取窗口连续前进,避免后续 tile 重复预取前面的区域。整行调用的额外偏移为 0。

这些改动不改变权重、量化方式、候选 token 或上下文状态语义。

## 交错测速

提示词为原始文本 `def fibonacci(n):`,4 个提示词 token、32 个生成 token,上下文容量 256,生成 2 线程、预填充 4 线程,贪心解码、重复惩罚 1。顺序为基线/优化/优化/基线/基线/优化。

| 构建 | 生成 token/s | 整个进程的 CPU 秒/请求 |
|---|---:|---:|
| 基线 | 1.21 | 49.62 |
| 优化 | 1.27 | 47.03 |
| 优化 | 1.27 | 47.77 |
| 基线 | 1.16 | 49.47 |
| 基线 | 1.20 | 50.14 |
| 优化 | 1.21 | 47.09 |

生成速度中位数 1.20 -> 1.27 token/s,约提升 5.8%；CPU 时间中位数 49.62 -> 47.09 秒/请求,约减少 5.1%。CPU 时间包含加载和提示词处理,不是单独的生成阶段时间。六次输出的 32 个 token ID 全部一致。

模型处于热缓存状态。这是单条提示词、三组短测,不是通用质量或长期性能保证。桌面和浏览器未关闭,后台 CPU 占用波动明显,芯片约 83-85°C。较早一轮的速度甚至在 0.64-1.26 token/s 间变化,所以不能把两次不交错的测试直接当成优化收益。

额外的隔离词表点积短测曾观察到双线程耗时中位数下降约 13%,但不应把这个比例套到整个生成流程。四行 Q6_K 合并计算版本在实验中更慢,未合入。

## 复现

保留两个独立编译的可执行文件,使用相同模型运行：

```
python3 bench/compare.py /path/to/baseline/pillm ./pillm \
  --model models/qwen3.5-2b-q4_0.gguf --tokens 32 --repeats 3 \
  --output /path/to/results.json
```

工具交错运行两版,记录二进制 SHA-256、命令、完整输出、生成 token ID、生成速度、墙钟时间和 CPU 时间。token 不一致时退出失败,要求人工检查,不会只报告更快的数字。不同提示词可以通过 `--prompt` 指定。

发布前仍运行 `make test`,包括独立数值检查、原架构合成模型、真实模型状态回放、分词 fixtures、HTTP 隔离和参考输出回归。默认线程保持 2/4；本轮没有证明提高线程数能稳定改善端到端速度。

## 2026-11-16: 消息前缀检查点

这一轮优化首个文本 token 的等待时间,生成运算核未改动。一个检查点保存在 assistant 生成前缀之前,用约 20.2 MB 保存递归/卷积状态；精确匹配 token 前缀后恢复,继续计算后缀。历史缩短、系统提示词变化或已保存前缀不匹配时会退回重算,详细状态语义见 [qwen35.md](qwen35.md)。

用同一个可执行文件启动两个本机服务,其中一个加 `--no-prefix-cache`,另一个采用默认配置：

```
./pillm -m models/qwen3.5-2b-q4_0.gguf --serve 8081 --no-prefix-cache
./pillm -m models/qwen3.5-2b-q4_0.gguf --serve 8082
```

在另一终端运行：

```
python3 bench/prefix.py http://127.0.0.1:8081 http://127.0.0.1:8082 \
  --repeats 3 --output /path/to/prefix-results.json
```

工具先预热,随后交错重复同一个提示词,从 SSE 流收到第一个非空文本片段时记录延迟。它要求基线 `cached_tokens=0`、候选 `cached_tokens>0`,并检查所有回答文本一致；同时单独报告生成 token/s。该测试测的是完整重复前缀命中场景,不是所有多轮对话都能达到相同收益。

本机三组交错短测（2026-11-16），提示词 `Reply with the word Paris.`，默认系统提示词，共 39 个输入 token，最多生成 4 token。候选每次复用 32 个消息前缀 token。首个文本 token 等待中位数从 12.78 秒降至 2.69 秒，减少约 79.0%。所有回答一致。生成 token/s 中位数分别为 1.20 和 1.35；输出很短、后台负载和温度会影响它，本轮并未修改生成内核，也不能据此推断长期生成吞吐提升。

另测一组实际续聊：先问 `Reply with the word Paris.`，收到 `Paris` 后追加 `Translate Paris to Chinese.`。关闭缓存时首字 18.46 秒，复用 32 token 的检查点后 7.82 秒，减少约 57.6%；两边均回答“巴黎”。这一组的生成速度分别为 1.24 和 1.22 token/s。续聊仅测了一组，不应当作所有对话的固定提升比例。


## 2026-11-16: 持续生成调优实验

新增可选 `-to N`，独立设置完整词表矩阵的线程数（也用于旧架构的两阶段候选粗排）。默认 `0` 继承 `-t`，不改变原有默认计算配置；不改变每行运算顺序、模型或量化。`-tb` 仍只控制提示词批量处理。可在服务器启动命令中使用同一选项。

本机已运行网页版请求、温度约 84–85°C 时，使用 `def fibonacci(n):`、24 个生成 token、上下文 256、贪心解码，交错比较 `-t 2 -tb 4` 与额外 `-to 4`：

| 顺序 | 输出层线程 | 生成 token/s | CPU 秒/整个请求 |
|---|---:|---:|---:|
| 基线 | 2 | 0.52 | 40.90 |
| 候选 | 4 | 0.54 | 42.30 |
| 候选 | 4 | 0.58 | 41.46 |
| 基线 | 2 | 0.55 | 41.61 |
| 基线 | 2 | 0.52 | 40.66 |
| 候选 | 4 | 0.52 | 39.91 |

六次生成 token ID 一致。输出层耗时中位数 477.6 → 387.8 ms/token，减少约 18.8%；整体生成速度中位数 0.52 → 0.54 token/s，约 3.8%，最后一组无整体提速。CPU 时间中位数略增。并行网页版请求、后台负载和热降频影响显著，此结果不能代表独占设备的吞吐，也不能证明稳定的整体收益。因此保留为可选调优参数，默认不提高线程数。

复现（同一可执行文件，分别传参数；完整命令保存在结果里）：

```
python3 bench/compare.py ./pillm ./pillm --tokens 24 --repeats 3 \
  --candidate-arg=-to --candidate-arg=4 --output /path/to/output-threads.json
```

另外两种尝试未合入：融合递归状态更新虽在隔离小内核里更快，整段生成中位数却为 0.90 → 0.87 token/s；展开 Q6_K 输出权重需额外约 544 MB，首轮完整生成仅 0.52 → 0.53 token/s，未见值得保留的收益，已提前停止该实验。模型和 swap 配置均未修改。

硬件实测温度到达 84–85°C；`vcgencmd` 曾读到约 1.58 GHz（配置上限 1.8 GHz）。官方说明 80–85°C 会逐步降频，裸板或被动散热应先改善持续散热，再用相同测试比较线程设置：[Raspberry Pi 温度与频率文档](https://www.raspberrypi.com/documentation/computers/config_txt.html)。降温收益需实测，不能直接推断成倍提速。
